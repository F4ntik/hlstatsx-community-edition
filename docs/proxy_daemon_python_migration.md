# План переписывания proxy-daemon.pl на Python

## 1. Цели и ограничения
- Сохранить существующие форматы входящих UDP-пакетов и команд управления (`PROXY Key=... PROXY ...`, `C;HEARTBEAT;`, `C;SERVERLIST;`, `C;RELOAD;`).
- Сохранить взаимодействие с MySQL (схема БД, таблицы `hlstats_Options`, `Proxy_Key`, `Proxy_Daemons`).
- Повторить поведение распределения серверов по демонам и механизм heartbeat.
- Обеспечить совместимость с текущими конфигурационными файлами (`hlstats.conf`).

## 2. Анализ текущего Perl-демона
- **Конфигурация**: чтение через `ConfigReaderSimple` и `HLstats.plib`, опции БД, порт, IP, уровень логирования.
- **БД**: подключение через `DBI`, выборка опций `Proxy_Key` и `Proxy_Daemons`.
- **Сетевое взаимодействие**: UDP-сервер, проксирование пакетов, контрольные команды с localhost, пересылка на суб-демоны.
- **Балансировка**: хеш `srv_list` для назначения демонов по принципу round-robin, реакция на изменение статуса демона.
- **Мониторинг**: периодический heartbeat каждые 30 секунд, проверка ответов `Heartbeat OK`.
- **Логирование**: `printEvent` из `HLstats.plib`.

## 3. Выбор архитектуры Python
### Вариант A: Асинхронный event loop (asyncio)
- Использовать `asyncio` + `asyncio.DatagramProtocol` для работы с UDP.
- Планировщик таймеров для heartbeat и пересылки.
- Подходит для большого числа одновременных соединений, легко масштабируется.

### Вариант B: Синхронный селектор (selectors + socket)
- Повторяет подход Perl-скрипта (блокирующий сокет с опросом).
- Проще мигрировать, но сложнее расширять и тестировать.

### Вариант C: Многопоточная модель
- Выделить потоки для приёма, heartbeat и пересылки.
- Более сложная синхронизация, оправдана при CPU-связанных задачах (не наш случай).

**Рекомендация**: использовать архитектуру на `asyncio` (Вариант A) для упрощения таймеров и асинхронных операций, при этом можно изолировать сетевую логику в отдельном классе и сохранить синхронный код работы с БД через `aiomysql` или обёртки над `mysqlclient` в executors.

## 4. Компоненты будущего решения
1. **Загрузка конфигурации**
   - Python-обёртка, совместимая с форматом `hlstats.conf` (ini). Можно использовать `configparser` и адаптировать парсер Perl, либо временно вызывать Perl для генерации? Предпочтительно — реализовать небольшой парсер с учётом текущей структуры.
   - Обеспечить опцию CLI (`argparse`) для `--configfile`, `--debug`.

2. **Логирование**
   - Создать модуль `logging` с форматированием времени как в `theTime` и уровнями (`NOTICE`, `CONTROL`, `BALANCE`, `E403`, `DAEMON`).
   - Возможность менять уровень логирования по `--debug`.

3. **Работа с БД**
   - Использовать `mysqlclient` (`MySQLdb`) или `mysql-connector-python`. Для `asyncio` — либо `aiomysql`, либо синхронные запросы через `run_in_executor`.
   - Реализовать функции `do_connect()`, `do_query()` аналогично `HLstats.plib`.

4. **Хранилище состояния**
   - Классы/структуры для:
     - списка демонов (`DaemonManager`),
     - маппинга сервер → демон (`ServerAssignment`).
   - Реализовать round-robin, мониторинг состояний (`curstate`, `oldstate`).

5. **Сетевой слой**
   - Класс `ProxyDatagramProtocol` (для asyncio) с обработчиками сообщений.
   - Поддержка локальных команд, проверки `proxy_key`, проксирования пакетов.
   - Отправка ответов и пересылка на демоны через `transport.sendto`.

6. **Heartbeat и контрольные задачи**
   - Периодическое задание (`asyncio.create_task`) для `check_heartbeat()`.
   - При получении ответов обновлять состояние демона, инициировать `reload` или перераспределение.

7. **Балансировка и failover**
   - Метод `assign_daemon()` для первоначальной и повторной привязки сервера.
   - Обработка состояний демона как в Perl (`up`, `down`, `n/a`).

8. **Совместимость по сообщениям**
   - Точное воспроизведение форматов строк.
   - Тримминг лишних префиксов (`$datagram =~ s/^.*RL /RL /g;`).

## 5. Пошаговый план миграции
1. **Подготовка окружения**
   - Определить минимальную версию Python (например, 3.10).
   - Обновить документацию и requirements (`mysqlclient`, `configparser` если нужен).

2. **Чтение конфигурации и CLI**
   - Реализовать модуль `config.py` для загрузки параметров.
   - Реализовать парсер аргументов, совместимый с Perl-опциями.

3. **Модуль доступа к БД**
   - Импортировать параметры БД, создать соединение, реализовать `get_proxy_key()` и чтение `Proxy_Daemons`.

4. **Модель данных**
   - Реализовать классы `Daemon`, `DaemonManager`, `ServerAssignment`.
   - Написать unit-тесты для round-robin распределения.

5. **Сетевой протокол**
   - Реализовать базовый UDP-сервер на `asyncio`.
   - Обработчики локальных команд, проверка ключа, пересылка пакетов без логики балансировки.

6. **Интеграция балансировки**
   - Подключить `assign_daemon()`, обновлять `srv_list` при сообщениях.

7. **Heartbeat и контроль состояния**
   - Добавить периодическую задачу.
   - Реализовать `reload_daemon()`.

8. **Логирование и совместимость сообщений**
   - Протестировать соответствие формата логов.

9. **Тестирование**
   - Модульные тесты (round-robin, парсинг команд).
   - Интеграционные тесты с эмулированными UDP-клиентами и моками демонов.
   - Тест с реальной БД (staging) и демонами.

10. **План внедрения**
    - Развернуть Python-версию параллельно Perl (порт +1) для теста.
    - После успешных тестов переключить production.
    - Оставить Perl как fallback до подтверждения стабильности.

## 6. Оценка трудоёмкости
- Анализ и дизайн: 1-2 дня.
- Реализация конфигурации и БД: 1 день.
- Сетевой слой и обработчики: 2-3 дня.
- Балансировка и heartbeat: 1-2 дня.
- Тестирование и фиксы: 2 дня.
- Всего: ~7-10 рабочих дней для одного разработчика, с учётом ревью и развёртывания.

## 7. Риски и рекомендации
- **Зависимости Perl**: убедиться, что логика `HLstats.plib` полностью воспроизведена в Python.
- **Асинхронность vs синхронность**: тестировать на нагрузке, чтобы избежать блокировок при медленных БД.
- **Совместимость формата**: добавить автотесты, сравнивающие строки Perl и Python.
- **Мониторинг**: добавить метрики/healthcheck при переписывании, чтобы упростить эксплуатацию.
