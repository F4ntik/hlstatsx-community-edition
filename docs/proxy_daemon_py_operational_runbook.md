# Руководство по вводу Python proxy-daemon в эксплуатацию

Документ описывает регламенты подготовки персонала, развёртывания Python-версии
`proxy-daemon`, мониторинга и пострелизных активностей. Содержимое охватывает
этапы из эпиков 7 и 8 плана миграции.

## 1. Подготовка команды и обучение

| Роль | Ответственности |
| ---- | ---------------- |
| SRE / DevOps | Настройка окружений, запуск пайплайнов деплоя, мониторинг, реагирование на инциденты. |
| DBA | Управление доступами MySQL, контроль миграций и мониторинг нагрузки БД. |
| Разработчики proxy-daemon | Поддержка кода, анализ логов, исправление дефектов. |
| Служба поддержки | Приём обращений игроков/серверов, эскалация инцидентов. |

1. Провести вводный воркшоп (1,5 часа) с демонстрацией архитектуры Python-демона,
   CLI-опций и отличий от Perl.
2. Разработчикам и SRE подготовить конспект «часто задаваемых вопросов» с типовыми
   ошибками запуска (`Proxy key mismatch`, ошибки подключения к БД, таймауты DNS).
3. Разместить ссылку на документацию (`proxy_daemon_python_migration.md`, `proxy_daemon_e2e_sandbox.md` и данный документ) во
   внутренней wiki и рассылке эксплуатационным командам.
4. Запланировать сессии Shadowing: первые 2 недели после запуска SRE дежурит
   совместно с разработчиком в рабочее время.

## 2. План поэтапного запуска

### 2.1 Staging

1. Подготовить staging-окружение согласно `scripts/proxy_daemon_py/fullstack/docker-compose.yml` или `scripts/proxy_daemon_py/e2e/docker-compose.yml`, если нужен только прокси-контур.
2. Выполнить деплой Python-демона с помощью Ansible playbook `deploy_proxy_daemon_py.yml` (см. репозиторий инфраструктуры).
3. Прописать переменные окружения `HLSTATS_CONF`, `PY_PROXY_DAEMON_LOG_LEVEL`, `PROM_PUSHGATEWAY`. Поддержка автоматического чтения этих переменных запланирована в bootstrap-скрипте (см. TODO в `scripts/proxy_daemon_py/bootstrap.py`); до мерджа обновления значения передаются вручную через аргументы контейнера/сервиса.
4. Запустить proxy daemon и минимум один `hlstats_py` worker в foreground-режиме на 24 часа, убедиться в стабильности heartbeat и отсутствии ошибок в логах `CONTROL/E403`.
5. Сравнить метрики распределения серверов с эталонным отчётом `docs/proxy_daemon_e2e_sandbox.md#expected-metrics`.
6. Подтвердить успешность автоматических тестов: `pytest scripts/proxy_daemon_py/tests`, `pytest scripts/proxy_daemon_py/e2e`.
7. Сформировать отчёт по результатам (таблица в Confluence) и получить согласование от владельца продукта.

### 2.2 Подготовка к production

1. Настроить CI/CD job `proxy-daemon-py-prod` с ручным подтверждением.
2. Проверить секреты в Vault: `mysql_proxy_daemon_prod`, `proxy_daemon_py_proxy_key`.
3. Убедиться, что в MySQL таблице `Proxy_Daemons` добавлена запись Python-инстанса со статусом `disabled`.
4. Настроить зеркалирование трафика (SPAN) для оценки нагрузки до переключения.
5. Согласовать окно внедрения (минимум 1 час, ночное время) с командами поддержки и сетевыми администраторами.

### 2.3 Переключение production

1. За 30 минут до начала — оповестить команды в общем канале #hlstats-rollout.
2. Перевести Python-демон в режим `enabled` в таблице `Proxy_Daemons`, оставить Perl-инстанс активным (режим параллельного приёма трафика с 10% нагрузкой через балансировщик).
3. Через 15 минут увеличить долю трафика до 50%, проанализировать метрики latency и ошибок UDP.
4. При отсутствии инцидентов в течение ещё 30 минут перевести 100% трафика на Python-демон, Perl-инстанс оставить в горячем резерве (`standby`).
5. Финализировать переключение, создав Change Record в ITSM со ссылкой на логи и графики.

## 3. Мониторинг и наблюдаемость

### 3.1 Prometheus

- Экспорт метрик из Python runtime через `/metrics` **ещё не реализован**. До появления Prometheus-экспортёра мониторинг строится по логам proxy daemon и `hlstats_py` worker plus внешнему pushgateway.
- Настроить scrape job `proxy-daemon-py` с интервалом 15 секунд.
- Дашборды Grafana:
  - `Proxy Daemon / Traffic`: скорость пакетов, ошибка переприсвоения сервера.
  - `Proxy Daemon / Heartbeat`: время ответа демонов, количество неуспешных heartbeat.
  - `Proxy Daemon / Database`: длительность запросов к MySQL и количество ретраев.

### 3.2 Логи и трассировки

- Отправлять логи в ELK через Filebeat, тег `service=proxy-daemon-py`.
- Настроить фильтры по уровням `E403` и `DAEMON` для быстрого поиска ошибок.
- Включить распределённый трейсинг (OpenTelemetry) для цепочки `UDP Packet -> Resolver -> DB`.

### 3.3 Алерты

| Условие | Severity | Действие |
| ------- | -------- | -------- |
| `heartbeat_unhealthy > 0` 5 минут подряд | Critical | Немедленно эскалировать на дежурного разработчика и SRE. |
| Ошибки отправки UDP > 1% 10 минут | Major | Проверить сетевые настройки, рассмотреть переключение на Perl-демон. |
| Время ответа БД > 200 мс 15 минут | Major | DBA анализирует нагрузку, возможно увеличение ресурсов. |
| Отсутствие метрик более 5 минут | Critical | Проверить экспортёр, сеть, состояние демона. |

## 4. Безопасность и комплаенс

1. Ежемесячный запуск Snyk CLI и Dependabot alerts для `scripts/proxy_daemon_py` и смежных пакетов (`hlstats_resolve_py`, `hlstats_awards_py`).
2. Контроль зависимостей: утверждение обновлений через Change Advisory Board.
3. Разграничение доступов:
   - Демону выдаётся отдельный MySQL-пользователь `hlstats_proxy_py` с ролями только на чтение/запись необходимых таблиц (`Proxy_Daemons`, `hlstats_Servers`).
   - Секреты хранятся в Vault, доступ через AppRole с ограниченным TTL (24 часа).
4. Логи с потенциальными персональными данными (IP) помечаются и хранятся не более 30 дней.
5. Раз в квартал проводить security review с участием команды безопасности (penetration test контура демона).

## 5. План отката

1. Условие для отката: SLA по доставке пакетов нарушается > 10 минут или наблюдается рост ошибок UDP > 5%.
2. Немедленные действия:
   - Установить статус Python-демона `disabled` в `Proxy_Daemons`.
   - Вернуть балансировщик на Perl-инстанс (100% трафика).
   - Выполнить Ansible playbook `rollback_proxy_daemon_py.yml` (остановка сервиса, сбор логов, архивирование; находится в инфраструктурном репозитории рядом с `deploy_proxy_daemon_py.yml`).
3. Восстановление: убедиться, что Perl-демон работает стабильно 30 минут.
4. Анализ: в течение 24 часов собрать рабочую группу, оформить RCA (Root Cause Analysis) и определить исправления.
5. Повторный запуск Python-демона только после устранения причин и обновления данного документа (если требуется).

## 6. Пострелизный анализ и непрерывное улучшение

1. Через 48 часов после финального переключения провести Postmortem-lite: оценить соблюдение планов, собрать обратную связь.
2. Собрать метрики: латентность, нагрузка на БД, количество инцидентов, сравнить с Perl-версией.
3. Службе поддержки подготовить отчёт о пользовательских обращениях, классифицировать по типам.
4. Сформировать backlog улучшений и приоритизировать в Jira.
5. Запланировать квартальный пересмотр настроек heartbeat, ретраев и порогов алертов.
